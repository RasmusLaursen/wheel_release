# wheel_test

The 'wheel_test' project was generated by using the default-python template.

* `src/`: Python source code for this project.
  * `src/wheel_test/`: Shared Python code that can be used by jobs and pipelines.
* `resources/`:  Resource configurations (jobs, pipelines, etc.)
* `tests/`: Unit tests for the shared Python code.
* `fixtures/`: Fixtures for data sets (primarily used for testing).
* `bundles/volume/`: Dedicated bundle that provisions the shared Unity Catalog release volume.

# Using this project using the CLI

The Databricks workspace and IDE extensions provide a graphical interface for working
with this project. It's also possible to interact with it directly using the CLI:

1. Authenticate to your Databricks workspace, if you have not done so already:
    ```
    $ databricks configure
    ```

2. To deploy a development copy of this project, type:
    ```
    $ databricks bundle deploy --target dev
    ```
    (Note that "dev" is the default target, so the `--target` parameter
    is optional here.)

    This deploys everything that's defined for this project.

3. Similarly, to deploy a production copy, type:
   ```
   $ databricks bundle deploy --target prod
   ```

4. To run a job or pipeline, use the "run" command:
   ```
   $ databricks bundle run
   ```

5. Finally, to run tests locally, use `pytest`:
   ```
   $ uv run pytest
   ```


# Release volume flow

This repo now uses two Databricks bundles:

1. The app bundle in [databricks.yml](databricks.yml) deploys the job and points the wheel dependency at a Unity Catalog volume.
2. The volume bundle in [bundles/volume/databricks.yml](bundles/volume/databricks.yml) creates the shared schema and volume used for release artifacts.

There is also a `user` target for development that uses the current workspace user's short name and local wheel output instead of a release version.

The production release flow is:

1. Deploy the shared volume bundle:
    ```
    databricks bundle deploy -t shared
    ```
2. Build the wheel for the release version.
3. Upload the wheel to:
    ```
    dbfs:/Volumes/<catalog>/<schema>/<volume>/<release-version>/
    ```
4. Deploy the app bundle with the matching `release_version` bundle variable.

The app bundle also uses a volume-backed `workspace.artifact_path` so bundle-managed build artifacts land in the same release area.


# GitHub release automation

The release workflow in [.github/workflows/release-wheel.yml](../.github/workflows/release-wheel.yml) does the following when a GitHub release is published:

1. Derives the release version from the tag.
2. Patches [pyproject.toml](pyproject.toml) so the built wheel version matches the release.
3. Deploys the shared volume bundle.
4. Creates a versioned folder in the Unity Catalog volume.
5. Uploads the built wheel into that folder.
6. Deploys the app bundle with the same release version.

The workflow defaults to the shared volume path `raw_dev.bundle_artifacts.wheel_release`.
If you need a different location, update the workflow env values in [.github/workflows/release-wheel.yml](../.github/workflows/release-wheel.yml).

The workflow expects these GitHub secrets:

* `DATABRICKS_HOST`
* `DATABRICKS_TOKEN`
